
Here is a detailed breakdown of what the **ML Correlation Brain** module does, what it checks, and how it operates within the Orbital Shield architecture.

### 🧠 Core Purpose

The **ML-Brain** module acts as the central intelligence hub of the simulated satellite ground station. It does **not** analyze raw data like telemetry or commands directly. Instead, it aggregates structured security alerts generated by four independent watcher modules:

1. **Downlink Module:** Watches telemetry for spoofing/anomalies.
2. **Uplink Module:** Watches commands for unauthorized/malformed requests.
3. **Firmware Module:** Watches firmware updates for integrity violations.
4. **Access Module:** Watches operator login behavior for suspicious activity.

**Its primary job is correlation:** It identifies when multiple, seemingly low-to-medium severity events across different subsystems are actually connected (e.g., same operator, same satellite, same time window) and merges them into a single, high-severity **Incident**.

> [!IMPORTANT] 
> **Advisory-Only Mode:** The ML-Brain has no enforcement power. It cannot block uplinks or revoke sessions. It solely flags, explains, and ranks incidents for human review (by a CISO). This ensures no automated system accidentally interrupts critical satellite operations due to a false positive.

---

### 🔍 What Does it Check? (The Rule Engine)

The system checks incoming events against a set of YAML-driven, easily configurable rules (found in `config/rules.yaml`). By default, it runs the following five checks over a sliding time window (usually 30 minutes):

1. **`cross_module_same_session` (RULE_001)**
   - **Trigger:** 2+ events from different modules sharing the *same operator session* within ~6.5 minutes.
   - **Meaning:** Indicates a compromised session spanning multiple subsystems.
   - **Incident Type:** `CROSS_MODULE_ATTACK`

2. **`escalating_severity_chain` (RULE_002)**
   - **Trigger:** Events on the *same satellite* progressing from LOW → MEDIUM → HIGH severity within 10 minutes.
   - **Meaning:** Suggests a developing, multi-stage attack or cascading failure.
   - **Incident Type:** `ESCALATING_INCIDENT`

3. **`firmware_plus_access_anomaly` (RULE_003)**
   - **Trigger:** A FIRMWARE integrity event and an ACCESS anomaly event overlapping on the *same satellite* within 15 minutes.
   - **Meaning:** Points to a supply-chain attack where a malicious firmware update is deployed using stolen credentials.
   - **Incident Type:** `SUPPLY_CHAIN_RISK`

4. **`multi_source_same_satellite` (RULE_004)**
   - **Trigger:** 3+ independent modules flagging alerts on the *same satellite* within 10 minutes.
   - **Meaning:** Consistent with a broad, multi-vector attack against a single asset.
   - **Incident Type:** `MULTI_VECTOR_ATTACK`

5. **`high_confidence_critical_pair` (RULE_005)**
   - **Trigger:** 2+ HIGH or CRITICAL severity events (with ≥85% confidence) from different modules targeting the *same operator or satellite* within ~6.5 minutes.
   - **Meaning:** Extremely high-fidelity signals pointing to a confirmed, critical threat.
   - **Incident Type:** `CRITICAL_THREAT_CLUSTER`

### 🧮 How It Scores Risk

When a rule is triggered, the engine calculates a **Risk Score** for the new Incident. This is an additive process based on the base scores of the contributing events:

- `FIRMWARE_TAMPERING`: +50
- `DATA_EXFILTRATION`: +40
- `UNAUTHORIZED_COMMAND` & `INTEGRITY_FAILURE`: +35
- `COMMAND_INJECTION`: +30
- `TELEMETRY_ANOMALY` & `REPLAY_ATTACK`: +25
- `SUSPICIOUS_LOGIN` & `ACCESS_VIOLATION`: +20
- `SIGNAL_INTERFERENCE`: +15
- **Multi-Source Bonus:** +10 points for every additional module involved beyond the first.

**Severity Mapping:**
- **> 70:** CRITICAL
- **> 40:** HIGH
- **> 20:** MEDIUM
- **≤ 20:** LOW

### 🤖 The Machine Learning & Feedback Loop

The "ML" in ML-Brain isn't just a buzzword; it operates on a **Human-in-the-Loop** retraining model to continuously improve its accuracy and reduce false positives without overriding human judgment.

1. **Scoring & Flagging:** The Rule Engine creates a scored incident. An ML layer (using a Random Forest Classifier) can optionally adjust this score slightly (up to ±15 points) based on historical patterns.
2. **Human Review:** The incident goes to a dashboard where a CISO reviews it and submits a verdict (`CONFIRMED_REAL` or `FALSE_POSITIVE`) back to the ML-Brain via the `/brain/feedback` API.
3. **Automated Adjustments (Retraining):** 
   - **Rule Widening:** If a specific rule generates 3+ false positives, the system automatically widens its time-window thresholds to be more forgiving.
   - **ML Retraining:** If there are enough new labeled verdicts (≥ 5), the system retrains the ML classifier to recognize new threat patterns.
   - **Auditing:** Every single change the ML makes to thresholds or weights is logged in the database as a `BRAIN_CONFIG_UPDATED` event for full transparency.

In short, the ML-Brain acts as an intelligent funnel: it takes noisy, isolated alerts from across the entire satellite ground station, logically links them together into high-confidence attack narratives, scores their risk, and learns from the CISO's feedback to get smarter over time.
